LM-1 — a general-purpose computer written in littleman

One CPU built from little men, rooms and pipes. Solve each contest problem by writing a program for it instead of hand-drawing a bespoke grid. One machine, sixteen programs.

1. The bet

Program score is max(width, height)² × avgTicks. A CPU is both large and slow, so LM-1 will score badly on purpose. That is the whole trade, and it is a good one:

test-case points = passing cases / total cases  (max 1)  → LM-1 earns this
ranking points   = teams you beat on score  (max 1)  → LM-1 earns ~0

A terrible score still collects the full test-case point on every problem it solves. Twelve graded problems × 1 point is the prize. Bespoke grids can reclaim the ranking half later, problem by problem. LM-1 is the safety net, not the optimum.

2. The machine, as blocks

Every box is a layout.py Container: a fixed-size ASCII block that declares local port coordinates. Every arrow is a pipe. You bind a reader or writer to a port near a wall; the layout solver places the containers and routes the lines, and _resolve_port validates that each pipe's touch cell really resolves to the port you intended. Blocks are swappable as long as they honour their port contract.

The ring runs through the CPU. The CPU is one of the ring's two rooms: it receives each word and immediately sends it back. That removes a room of latency and makes fetch strictly lock-step — so there is no prefetch, and therefore no branch-flush hazard to reason about.

4. The whole machine running

ROM + code ring + CPU + output, with a two-opcode ISA: word 0 means halt, any positive word means emit this value. Program: 7 8 9 0. Every frame below is a real interpreter snapshot, not an animation of an idea.

tick 0/75

It emits 7 8 9 and the CPU man halts on the 0 word. The left room is LOOP — R accepts from both the ROM and the CPU, s feeds the CPU. The right room is the CPU: > re-orients, r fetches, s recirculates into the ring, X decodes on sign, H halts, and the lower lanes carry the emit micro-program plus the walk back to the fetch cell.

Heading is part of a unit's port contract. The first version of this slice hung with no output. Every glyph was correct — but the fetch r was entered heading south, so after receiving, the man stepped onto the return lane's ^, which sent him straight back onto r. A two-cell loop that refetched forever and never reached the decoder. Entry ports must declare (cell, heading), and the generator has to assert it.

5. Where the 20 ticks go

The CPU man's cycle is 18 cells plus about 2 ticks of blocking. Counting the cells he actually walks:

Half the instruction budget is the walk home. Fetch, decode and execute are 8 cells between them; the return path is 10. That makes return-path length — not the ALU, not the decoder — the first thing to optimise, and it argues for lane ends that finish adjacent to the fetch cell rather than at the far wall.

6. Decoding with the backpack

b loads the opcode into the backpack; then ] and x peel one bit per cell and turn. A depth-k trie dispatches 2k opcodes and each leaf is a distinct cell — exactly where that opcode's micro-program starts. No comparison chain, no jump table.

Lane rows run 0, 2, 1, 3 top to bottom: the trie sorts its leaves in bit-reversed order. That is the concrete reason opcode numbering is a free layout variable — you choose which opcode lands next to which wall, and therefore which pipe its r and s resolve to.

7. Staging by semester

Semesters do not map onto capability tiers — the tiers cut across them. But grouping by semester shows something useful: Semester 3 is uniformly "big RAM plus nested loops", which is precisely where a CPU beats hand-drawing, and Semester 1 spans the entire range on its own.

problemneedsRAM slotsstagestatus

One slot is mandatory, not optional. Even triangle cannot run on ACC alone: A is destroyed by every instruction fetch, so a loop can never hold two live values. The 8-slot STORE stub is therefore part of the CPU from day one — the accumulator-only tier is effectively empty.

matmul looks infeasible on a single delay line. A 16×16 product needs ~8,450 memory accesses; at 768 words a delay-line access averages ~2,300 ticks, so ~19M ticks against a 5M cap. Banked memory or a bespoke solution — flagged now rather than discovered late.
